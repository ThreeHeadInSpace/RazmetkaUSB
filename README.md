# RazmetkaUSB

**JS для авторазметки сессий в JAICP**

Bookmarklet для быстрой разметки диалогов бота в JAICP меткой `Верно`.

---

Как сейчас работает кнопка разметки v8.5
1. Запуск скрипта

После нажатия на кнопку запускается bookmarklet verno-marking-bookmarklet v8.5.

Скрипт находит на странице все сообщения диалога — элементы:

div.Message_container

После этого каждое сообщение будет отдельно проверено: нужно его разметить как «Верно» или необходимо пропустить.

2. Перед разметкой скрипт устанавливает метки

Сначала скрипт пытается найти и нажать метку проверяющего:

«.Ведерников И. Ю.»

Затем пытается найти верхнюю кнопку:

«Верно»

Если соответствующая кнопка на странице не найдена, скрипт просто продолжает работу.

3. Из каждого сообщения извлекаются основные данные

Для каждого сообщения определяются:

Class — значение phraseClass;
State — значение phraseState;
текст сообщения клиента;
текст ответа бота;
быстрые кнопки, которые бот показывал клиенту в предыдущем сообщении.

Текст дополнительно нормализуется:

переводится в нижний регистр;
лишние пробелы схлопываются;
пробелы в начале и конце удаляются.

Для некоторых текстовых проверок также удаляется пунктуация по краям сообщения.

4. Главный принцип работы

Логика сейчас построена по принципу:

По умолчанию сообщение нужно разметить «Верно».
Не размечаем его только в том случае, если сработало одно из явно заданных исключений.

То есть скрипт ищет причину пропустить сообщение — skipReason.

Если причины нет → сообщение размечается.

5. Первое и самое приоритетное правило — NoMatch

Если в Class или State содержится:

nomatch

то сообщение обязательно идёт в разметку.

При этом остальные исключения уже не проверяются.

То есть:

NoMatch имеет приоритет над приветствиями, благодарностями, ошибками, классами-исключениями и другими правилами.

Результат:

NoMatch → «Верно»

6. Отдельная специальная логика для TransferToOperator

Если в Class или State обнаружен:

transfertooperator

включается отдельная ветка проверки.

В этом случае сообщение пропускается только для конкретной пары:

Class содержит generalstates/clarity;
State содержит generalstates/transfertooperator.

Такая комбинация:

Clarity + TransferToOperator → пропустить

Все остальные сообщения с TransferToOperator сейчас отправляются в разметку.

И здесь есть особенно важный нюанс текущей v8.5:

Если обнаружен TransferToOperator, скрипт заканчивает проверку на этом этапе и не доходит до текстовых исключений ниже.

Поэтому правила вроде:

«оператор»;
«позовите оператора»;
«спасибо»;
приветствие;
техническая ошибка;
и т. д.

для такого сообщения уже не проверяются.

Это одна из наиболее важных особенностей текущей архитектуры скрипта.

7. Исключения по Class и State

Если сообщение не NoMatch и для него не сработала специальная ветка TransferToOperator, проверяются Class и State.

Сообщение пропускается, если Class содержит:

selling;
/handlers/timeouthandler.

Сообщение также пропускается, если State содержит:

anyerror;
fileevent;
timeouthandler;
limithandler.

Результат:

совпадение с исключённым Class/State → не размечать

8. Ответ клиента через кнопку бота

Далее проверяется, не нажал ли клиент одну из быстрых кнопок, которые бот показал в предыдущем сообщении.

Алгоритм такой:

Берётся текст текущего сообщения клиента.
Берутся названия всех быстрых кнопок из предыдущего сообщения бота.
Если текст клиента полностью совпадает с текстом одной из кнопок, считается, что клиент просто нажал quick reply.

Например, бот показал:

Да | Нет

Следующее сообщение клиента:

Да

Такое сообщение:

пропускается и не размечается.

9. Чистые приветствия

Если сообщение состоит только из приветствия, оно не размечается.

Сейчас распознаются варианты вроде:

«Добрый день»;
«Доброго дня»;
«День добрый»;
«Добрый вечер»;
«Доброго вечера»;
«Доброе утро»;
«Доброго утра»;
«Доброй ночи»;
«Здравствуйте»;
«Здравствуй»;
«Привет»;
«Приветствую»;
«Доброго времени суток».

Пунктуация по краям не мешает проверке.

Например:

Здравствуйте!

→ пропустить

Но если вместе с приветствием клиент задаёт вопрос:

Здравствуйте, как закрыть карту?

→ это уже не чистое приветствие, поэтому данное исключение не срабатывает.

10. Чистые прощания

Сообщение не размечается, если целиком является прощанием.

Поддерживаются, например:

«Пока»;
«До свидания»;
«Досвидания»;
«Досвидос»;
«Всего доброго»;
«Всего вам доброго»;
«Всего хорошего»;
«Хорошего дня»;
«Хорошего вечера»;
«До встречи»;
«Прощай»;
«Прощайте».

То есть:

только прощание → пропустить

11. Чистые благодарности

Следующее исключение — сообщение, которое состоит только из благодарности.

Распознаются различные варианты:

«Спасибо»;
«Спасибо вам»;
«Спасибо большое»;
«Спасибо огромное»;
«Спасибо вам большое»;
«Большое спасибо»;
«Огромное спасибо»;
«Огромнейшее спасибо»;
«Благодарю»;
«Благодарю вас».

Например:

Спасибо!

→ не размечается

Но:

Спасибо, а как закрыть карту?

→ это уже не чистая благодарность, поэтому сообщение продолжает участвовать в разметке.

12. Стандартная техническая ошибка бота

Скрипт проверяет не только сообщение клиента, но и ответ бота.

Если в ответе содержится стандартный текст:

«Возникла техническая ошибка. Пожалуйста, для продолжения консультации обратитесь на горячую линию банка…»

с номером 8-800-250-57-57,

такой кейс:

пропускается и не размечается.

Кнопки из ответа бота перед этой проверкой удаляются, чтобы они не влияли на сравнение.

13. Чистый запрос оператора / человека

В v8.5 добавлено отдельное текстовое исключение для сообщений, смысл которых заключается только в просьбе соединить с человеком.

Скрипт понимает различные формы слов:

оператор;
специалист;
сотрудник;
консультант;
менеджер;
человек;
живой человек.

Также распознаются различные конструкции.

Например:

«оператор»;
«специалист»;
«живой человек»;
«мне нужен оператор»;
«нужен специалист»;
«позовите оператора»;
«дайте специалиста»;
«подключите сотрудника»;
«соедините меня с оператором»;
«свяжите меня с консультантом»;
«переведите на оператора»;
«переключите меня на специалиста»;
«как связаться с оператором»;
«поговорить с человеком»;
«связь с оператором».

Слово:

пожалуйста

перед этой проверкой специально удаляется.

Поэтому, например:

Соедините меня, пожалуйста, с оператором

также может быть распознано как чистый запрос человека.

Если сообщение соответствует одному из этих шаблонов:

не размечать.

При этом это правило работает только если сообщение дошло до данного этапа проверки. Специальная ветка TransferToOperator, описанная выше, выполняется раньше.

14. DontHaveQuestions

Для класса:

/donthavequestions

работает отдельная логика.

Важно: одного наличия этого класса недостаточно.

Скрипт дополнительно проверяет текст клиента.

Пропускаются, например:

«Нет»;
«Нет, спасибо»;
«Нет спасибо большое»;
«Нет, не нужно, спасибо»;
«Всё»;
«Все»;
«Всё, спасибо»;
«Вопросов нет»;
«Вопросов больше нет»;
«Больше вопросов нет»;
«Нет больше вопросов»;
«Спасибо, вопросов больше нет».

То есть принцип сейчас такой:

Class = /donthavequestions + подходящий короткий ответ клиента → не размечать.

Если Class /donthavequestions, но сообщение не совпало с разрешённым шаблоном, оно продолжает размечаться.

15. Если ни одно исключение не сработало

Сообщение считается требующим проверки.

Скрипт ищет внутри него кнопку:

«Верно»

и нажимает её.

То есть:

нет причины для пропуска → нажать «Верно»

16. Визуальное выделение автоматически размеченных сообщений

После автоматического нажатия «Верно» сообщение дополнительно выделяется.

Добавляются:

оранжевая полоса слева;
светло-оранжевый фон;
небольшой внутренний отступ;
подпись:

● Размечено автоматически — проверьте

Это позволяет глазами отличить сообщения, которые разметил скрипт, от остальных.

17. Скрипт ведёт журнал в консоли

Перед фактической разметкой для каждого сообщения в консоль выводятся:

номер сообщения;
Class;
State;
текст клиента;
будет сообщение пропущено или нет;
конкретная причина пропуска — skipReason.

Причины могут быть такими:

classStatePair
classOrState
buttonClickResponse
greetingMessage
goodbyeMessage
thanksMessage
technicalErrorText
pureOperatorRequest
noMoreQuestionsMessage

После проверки всех сообщений выводится итог:

«размечено X, пропущено Y»

18. Важный нюанс счётчика

Есть небольшая техническая особенность.

markedCount сейчас означает фактически:

«сообщений, которые скрипт решил разметить»

а не гарантированное количество успешно нажатых кнопок.

То есть сначала скрипт может посчитать сообщение как подлежащее разметке, но если внутри конкретного контейнера кнопка «Верно» почему-то отсутствует, реального клика не произойдёт.

19. Текущая последовательность принятия решения

Если свести всю v8.5 к одной цепочке, сейчас она выглядит так:

Сообщение →
NoMatch? → размечаем →
TransferToOperator? → проверяем только специальную пару →
исключённый Class/State? → пропускаем →
ответ через кнопку? → пропускаем →
чистое приветствие? → пропускаем →
чистое прощание? → пропускаем →
чистая благодарность? → пропускаем →
техническая ошибка? → пропускаем →
чистый запрос оператора? → пропускаем →
DontHaveQuestions + подходящий ответ? → пропускаем →
ничего не сработало → нажимаем «Верно».
